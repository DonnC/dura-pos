# The Shop Hub

A standalone Apps Script web app in the shop's own Google account, running as
the owner. It's plain JavaScript with JSDoc types and no build step, because
that is the easiest thing to debug in the Apps Script editor (decision 0006).

## Read first

- `backend/hub/README.md`: layout, known limits and the quota rules.
- `backend/hub/PROTOCOL.md`: the contract with phones. It's backend-neutral.
- `handbook/decisions/0005-shop-hub-as-the-backend.md`.
- `notes/15-apps-script-route.md` for the reasoning and the spikes still owed.

## Check Google's current docs

Use <https://developers.google.com/apps-script> for every API and limit, not
memory. Quotas differ by account type. When a call shape isn't on Google's pages,
say so in the README's known limits, because tests here run on fakes.

## How a request flows

`doPost` (`web_app.js`) parses JSON and calls `handleRequest_`, which checks the
envelope, authenticates the device (`request_auth.js`), and runs the handler from
`handlerFor_`. Every reply has the same envelope, and an unexpected failure is
reported only as `internal_error`, never with its message.

A GET serves the public shop page, usually from the cache. Provider callbacks
arrive at `?cb=<provider>`, skip the envelope and always answer
plain `ok`.

| File | What it owns |
|---|---|
| `devices.js` | Pairing, device records, revoking |
| `journal.js`, `journal_drive.js` | Batch acceptance and storage |
| `views.js` | Journal rows into Sheets |
| `setup.js`, `templates.js`, `drive_files.js`, `sheet_cells.js` | Shop setup |
| `master_data.js` | `changes.pull`, the `Stock` and `Balances` rows |
| `jobs.js` | Timers, the daily pass, the `Months` tab, `status` |
| `payments.js`, `paynow.js` | Provider-neutral payments, and the Paynow adapter |
| `attachments.js` | Photos and exports |
| `storefront.js` | `doGet`: the public shop page. Only the fields named in `storefrontData_` can appear, and owner text is always escaped |
| `view_contract.js` | Generated by `dura_templates`: never edit it |

## Code rules

- **Internal functions end in `_`,** so Apps Script hides them from the editor
  and from `google.script.run`. Only `doGet`, `doPost`, `shopProducts`, `runViews`
  and `dailyJob` don't.
- **Top-level constants use `var`.** Files may load in any order, so nothing at
  load time may depend on another file. That's why `handlerFor_` and
  `paymentAdapter_` build their answers at call time.
- **Handlers take `(request, services, device)`.** Reach Google through
  `services` or the thin wrappers, so tests can replace them.
- **Amounts travel as decimal strings** and become numbers only in a sheet cell.
- **Errors** use `hubError_` with one of the six categories in `PROTOCOL.md`.
- **No secrets, payloads or error messages in logs:** log `error.name` at most.

## Saving quota is a design rule

- **Script Properties:** one `getProperties` per execution, plus one after the
  lock (`withLock_` reloads). Write several values with `setMany`. The store
  holds 500 KB, so anything that grows per sale doesn't belong there; `pay:` rows
  are dropped after three days for this reason.
- **Drive:** always `fields: 'id'`. Files are found through the registry, never by
  name.
- **Sheets:** one batched call per workbook. Find columns by heading, cached by
  `sheetInfo_`. Skip a write when a stored hash shows nothing changed.
- **The lock** covers state changes, not slow outside calls. Never hold it around
  a provider request from a phone.
- **Timers** share a daily runtime budget, so a timer with nothing to do must stop
  after one property read.

## State lives in Script Properties

| Keys | Meaning |
|---|---|
| `device:P2`, `devices:next` | Paired phones, with their secrets |
| `journal:P2`, `view:P2`, `seen:P2` | Batches stored, batches in views, last upload |
| `viewq:P2:000124` | Batches waiting for views |
| `row:<file>:<tab>` | The next row to write |
| `file:*` | The registry: `file:myshop`, `file:month:2026-11`, `file:year:2026` |
| `filled:*`, `hash:*`, `rows:*`, `summary:*`, `months:*` | What's already written |
| `paykey:paynow:USD`, `pay:<reference>` | Provider keys, and open payments |

Secrets stay in Script Properties. They never go in a sheet, log, reply or export.

## Guarantees to protect

- **Exactly-once views without reading the sheet.** Rows go to explicit positions,
  and pointers move with the batch's `view:` mark in one `setMany`, after all
  writes succeed. A retry overwrites the same rows.
- **A view failure never fails an upload.** The batch is already stored and stays
  queued.
- **Resumable setup.** Each step records its ID as soon as it succeeds.
- **A failing daily step doesn't stop the others** (`dailyStep_`).
- **Unknown tables and fields are counted and skipped,** so a newer phone can't
  jam an older hub.
- **Sheets are proposals.** Bad rows from the owner are skipped and listed, never
  passed to phones.
- **Only the hub writes `hubOnly` tables** such as `Months`.

## Payment rules

- Paid comes only from the provider's status check, with its hash verified and
  the amount matched. A callback is a hint that makes the hub check sooner.
- A charge is never repeated. The reference is claimed before the provider is
  called, and a lost reply stays `unknown`.
- A new provider is one file behind `paymentAdapter_`: keys, start, check,
  callback. Keep the order of hashed fields exactly as the provider's docs give it.

`handbook/engineering/11-payments.md` has the flows and the adapter contract.

## Adding or changing an action

1. Write the test first, with `readyShop` and friends from `test/support/`. Extend
   `google_fakes.js` to match the real API's shape, and see the test fail.
2. Add the handler, and its `case` in `handlerFor_`.
3. Update `PROTOCOL.md`. If phones can use it, also update the port table in
   decision 0005.
4. Update the README's layout, limits and quota notes, and `CHANGELOG.md`.
5. For a security check, break it on purpose and confirm a test fails.
6. Run this from `backend/hub`:

```text
npm install
npm run verify
```

## Trying it for real

`npm run trial` from `backend/hub` installs a hub on the signed-in Google account and
runs every check; `handbook/engineering/10-real-account-test.md` is the guide. When a
new action matters on real Google, add a check to `backend/hub/tools/trial.js`.

Give people the `/a/~/macros/s/<ID>/exec` address for the shop page: the plain one can
fail in a browser signed in to several Google accounts.

## Done when

`npm run verify` passes, the docs match, and anything assumed about Google or a
provider is listed under the README's known limits. Tests prove the logic against
fakes, not Google: report the two separately. Never deploy into anyone's account
without being asked.
