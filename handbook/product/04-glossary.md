# Glossary

The words used across the notes, the handbook and the code.

## The product

| Term | Meaning |
|---|---|
| **Dura** | Shona for a granary. The project's name |
| **Business** | One trading entity, usually one TIN. It has its own folder in Drive, `Dura POS/<business>/`. One Google account can hold several |
| **Owner** | The person who controls the business's Google account, keys and settings |
| **Cashier** | The selling role. Signs in with their own PIN; an email address is not required. Use this role name throughout current UI, never Seller, Staff or User as a substitute |
| **Manager** | A possible future permission role; not a third role in the current Owner/Cashier design |
| **Location** | A shop, branch, stall or store. It's a column in the records, not a separate folder |
| **Device** | One app installation on a mobile, tablet or other supported hardware. Device IDs such as `P1` remain technical identifiers. Devices and cashiers are separate: several cashiers may share a device |
| **Stock** | Products and quantities held for sale. Use Stock for navigation and stock levels; do not alternate it with Inventory |
| **Stock take** | Physically counting stock and reviewing differences. Use this for the counting task; it is separate from cash-up |
| **Pricing currency** | The one currency that product prices are set in, chosen by the owner at setup. No default |
| **Rate policy** | How exchange rates apply: one daily rate, or the latest rate. Every payment records the rate it used |
| **Kept change** | Change the shop owes a customer ("I'll keep your change"), recorded with its currency until it's used or paid out |
| **Cash-up** | Counting the till at the end of a shift and comparing it with what Dura expects, per currency |
| **Handover** | Passing cash from one cashier, or the till, to another person, with any float kept back |
| **Practice mode** | A fictional shop with fake payment and fiscal services, for training and trying Dura |
| **Test mode** | A separate copy of a real shop (`(TEST)` folder, separate database, `T-` IDs) using ZIMRA's test environment and payment sandboxes |
| **Live** | Real trading. Test and practice data can never mix with it |

## Current interface wording

Role labels are **Owner** and **Cashier**. Use **Cashiers** for the collection.
Use **Device** for an installation, including in pairing, access and reports;
use **mobile number** for a contact number. Mobile/tablet describe viewport
types in design tools, not different account or permission nouns. Use **till**
for responsibility for the drawer/shift, not as another name for the device.

Older notes and technical identifiers may retain `worker`, `seller`, `staff`
or `phone` for compatibility. They do not define current display copy. This
design pass establishes the vocabulary; adopting it in Flutter is separate
implementation work. See the current design language contract in
`handbook/design/prototype/cdx/-cdx-language-roles.md`.

## Records

| Term | Meaning |
|---|---|
| **Local database** | The phone's own store (Drift/SQLite). Selling runs from it, offline |
| **Event** | One recorded fact, such as `sale.completed`. It has a stable ID and is never edited. A correction is a new linked event |
| **Outbox** | Events saved on the phone but not yet confirmed as uploaded |
| **Journal** | The append-only history of events, uploaded as sealed batch files (`P1-000001.json`) to the owner's Drive. The shared record of truth |
| **Batch** | A sealed group of events uploaded together. Its ID and content never change, so a retry can't double-count |
| **View** | A Google Sheet tab built from the journal for people to read. A damaged view can be rebuilt |
| **View writer** | The one component allowed to build the Sheets views: the Shop Hub |
| **Input tab** | A green tab the owner may edit (products, prices, rates). Edits are checked before Dura accepts them |
| **`My Shop`** | The permanent workbook: products, contacts, settings, lists, rates, stock and summaries |
| **Monthly workbook** | One file per month, e.g. `2026-10 October`: sales, payments, stock movements, cash-ups, Activity and a summary |
| **Activity** | The audit trail: who did what, who approved it, and why. A tab in each monthly workbook |
| **`Lists`** | The tab that every dropdown in the workbooks reads from |
| **`business.json`** | A small directory file that lets a new phone find the business's files. Holds no secrets |
| **Template** | A clean workbook generated by the Python generator, which the app copies for a new shop or month |
| **Sample shop** | The fictional shop in `backend/templates/sample/Dura POS/`, built by the `dura_templates` generator in `backend/templates/`: the executable spec of every file, tab and formula |
| **Layout version** | The version of a workbook's structure, used for safe upgrades |

## Connections

| Term | Meaning |
|---|---|
| **Shop Hub** | The shop's own backend: a standalone Google Apps Script web app in the owner's account, running as the owner. Everything that reaches Google goes through it: uploads, Sheets views, files, photos, payments and scheduled jobs. Never needed to complete a sale, and never touches ZIMRA |
| **Pairing** | Giving a phone its own secret (by QR code from the owner's phone) so it can sign its requests to the hub |
| **Gateway / provider** | A payment service such as Paynow or ZB Smile&Pay. Each is an adapter behind one payment interface |
| **Adapter** | Code that connects one contract to one outside service: a payment provider, printer, store or fiscal SDK |
| **Callback** | A message from a payment provider saying a payment changed. Only a hint: a payment is marked paid only after Dura checks |
| **Settlement** | The provider paying collected money to the shop's bank or wallet, less fees. Not a new sale |
| **`drive.file`** | The Google permission the Shop Hub uses for Drive. It reaches only files the hub created, not the rest of the owner's Drive |
| **Backend port** | The single interface in `dura_core` through which the app reaches any backend. The Shop Hub is its first adapter |
| **Device secret** | The key a phone receives when it pairs, used to sign every request to the hub. Never a Google token |

## ZIMRA

| Term | Meaning |
|---|---|
| **ZIMRA** | The Zimbabwe Revenue Authority |
| **FDMS** | ZIMRA's Fiscalisation Data Management System, which receives fiscal receipts |
| **Fiscalisation** | Issuing tax receipts that ZIMRA signs and records. Optional per business in Dura, following the business's own obligations |
| **Fiscal device** | In Dura, each selling phone is its own ZIMRA device, under its location's ZIMRA branch |
| **Fiscal day** | ZIMRA's trading-day unit, opened and closed by the device, with a Z report at the close |
| **fzimra** | The open-source Android ZIMRA SDK ([`DonnC/zimra-fdms-android`](https://github.com/DonnC/zimra-fdms-android)). Dura uses it through a typed bridge, and its keys never leave the phone |
| **HS code** | A product classification code. ZIMRA's list is in `data/zimra_hs_codes.csv` |
