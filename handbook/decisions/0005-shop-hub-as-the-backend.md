# Decision 0005: the shop's own Apps Script hub is the backend, behind one port

Status: Accepted; open points need the spikes in note 15 §16
Date: 3 November 2026
Roadmap slice: 3 (owner records) and 6 (hub, staff and payments)

## Problem and evidence

Under decision 0003, phones called the Drive and Sheets REST APIs directly.
Those calls count against the Google Cloud project that registers the app,
which is Dura's, and that project is shared by every shop.

- **Shared limits:** Sheets allows 300 requests a minute per project.
- **Coming charges:** Google's Sheets and Drive pages say exceeding the quota
  is "planned to incur charges to your Google Cloud billing account later in
  2026".

That puts a growing dependency and a billing risk on Dura, against the rule
that each shop carries its own costs. Every phone would also hold a token for
the owner's Drive.

An Apps Script web app runs as the owner. Its API use goes through a Cloud
project that Google creates and manages for that script, so it counts against
the shop's own account.

Research: [note 15](../../notes/15-apps-script-route.md).

## Decision

1. **The Shop Hub is the only way records reach the shop's Google account.**
   - The hub is a standalone Apps Script web app, created in the owner's
     account and run as the owner.
   - Every upload, file creation, Sheets view, photo, export, payment and
     scheduled job goes through it.
   - Phones never call the Drive or Sheets APIs.
2. **Dura's Google Cloud project is used only to install and update the hub,**
   from the owner's phone, through the Apps Script API. That's about four
   requests per install or update. The owner's Google token is discarded
   afterwards.
3. **Phones pair with the hub, not with Google.**
   - The owner's phone pairs during install, with a one-time install code.
   - Other phones pair by a QR code the owner's phone shows.
   - Each phone holds its own device secret and signs every request. No phone
     holds a Google token.
4. **The hub is always the single view writer.** This replaces decision 0003
   point 5: there's no owner-phone writer and no handover between writers.
5. **Selling never waits for the hub.**
   - A sale completes on the phone and queues until the hub accepts it.
   - A shop can sell offline before the hub is installed.
6. **The Flutter app is server-agnostic.**
   - Everything the app needs from a backend goes through one port in
     `dura_core`. It doesn't depend on Google or Apps Script.
   - The Apps Script hub is one adapter behind that port. Its client code
     lives in one package, `dura_hub`.
   - Moving away from Google means writing another adapter that speaks the
     same protocol, or another implementation of the port. Screens, rules and
     the local database don't change.
7. **One protocol, owned by Dura.** The hub protocol (versioned JSON messages,
   signed by the device) is specified in `backend/hub/PROTOCOL.md`. It describes
   business operations, not Google APIs, so any backend can implement it.

## The port

The app's view of any backend:

| Operation | Meaning |
|---|---|
| `pair(code, deviceName)` | Exchange a pairing code for a device ID and secret |
| `putJournal(batch)` | Upload a sealed batch; returns the highest sequence accepted |
| `pullChanges(since)` | Master data changed since a version: products, prices, rates, staff, settings |
| `createPairingCode()` | Owner only: a short-lived code to add a phone |
| `revokeDevice(id)` | Owner only |
| `uploadAttachment(kind, id, bytes)` | Product or supplier-invoice photo |
| `requestExport(period, format)` | Excel or CSV export |
| `startPayment(request)`, `checkPayment(ref)` | Through the shop's provider keys |
| `status()` | Registry health, view lag, last seen per phone, hub version |

Errors are typed, using the categories in the testing policy:

- validation;
- permission;
- authentication needed;
- retryable unavailable;
- unknown external outcome;
- integrity conflict.

No Google type appears in the port.

## Compatibility and migration

- **Nothing is built,** so no data migrates.
- **Decision 0003 still holds,** except points 4 and 5:
  - the journal is the history;
  - Sheets are views and checked inputs;
  - workbooks are template-first;
  - there's no destructive year end.
- **What stays from decision 0003, point 6:** templates are generated by
  Python and published with each release. The hub, not the phone, fetches
  them, checks their SHA-256, and converts them into Google Sheets in the
  shop's folder.
- **Decision 0003's acceptance item 7** (`drive.file` on a second phone) no
  longer applies. It's replaced by note 15's scope spike.
- **The hub's code lives in `backend/hub/`** (decision 0006). It's versioned with the protocol, and
  installed per shop at a pinned version.

## Acceptance and reversal

- The spikes in note 15 §16 pass, starting with a timed install on a fresh
  Gmail account.
- A `dura_core` contract test suite for the port runs against a fake backend
  and against the hub adapter. The same tests must pass for any future
  backend.
- **Reversal:** if the install or the hub's limits prove unworkable, write a
  direct-REST adapter behind the same port. The app above the port stays the
  same, by design.
